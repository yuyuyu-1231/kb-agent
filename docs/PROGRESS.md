**第 2 项验收结果（11/8 实测，12 轮 × 2 组）：**

| 阶段 | 裁剪预算 | 峰值 token | 首次裁剪 | 截断 | 末轮记忆 |
|---|---|---|---|---|---|
| A | 30000（真实） | 27592 | **未触发** | 0 轮 | 记得 |
| B | 6000（模拟） | 16101 | **第 1 轮** | **12 轮全部** | 记得 |

**结论：**

- **裁剪逻辑正确**：预算 6000 时 12 轮每轮都裁，不崩、不丢关键信息
- **真实预算对 12 轮对话绰绰有余**（峰值 27592 < 30000）
- 末轮问“总结假期规则”，两组都答得出 5/10/15 天 →
  **即使历史被裁，模型靠工具重新检索也能兜住**

**一个附带发现**：三份不同排版的语料（双栏 / 带页眉页脚 / 无结构长文）
都正常入库（5 / 6 / 17 个 chunk），但**页眉页脚剔除都是 0 块**。

原因不是 bug：`detect_margin_keys` 要求 `total_pages >= 3` 才启动检测，
而变体每份只有 2 页。**这是正确行为**（页数太少无法判断“重复”），
但意味着：要验证页眉页脚剔除，语料至少要有 3 页。

**第 3 项验收结果（11/8，用剧本化假模型）：**

| 场景 | 构造 | stop_reason | 步数 |
|---|---|---|---|
| A 重复动作 | 一次返回 2 个参数相同的 tool_calls | `loop_detected` | 1 |
| B 轮数超限 | 每轮都调工具、永不收敛 | `max_steps` | 3 |
| C 预算耗尽 | 一次响应烧穿 50 token 预算 | `budget_exhausted` | 1 |

**`_pad_skipped_tool_calls` 第一次被执行**（之前从未跑过）：
补 1 条占位消息，`tool_call_id=c2`，内容 `{"error": "已熔断，本次工具调用未执行"}` ✅

**验证过程中发现一个真 bug（已修）：**

`loop.py` 里有 `used_tokens = max(used_tokens, fit.estimated_tokens)`，
把「当前上下文**大小**」混进了「**累计消耗**」。后果：`token_budget=50` 时，
光 system prompt 就 400 token，于是 **第 0 轮就熔断，steps=0，模型一次都没被调用**。

已删掉该行并加注释。修复后 C 场景 steps 从 0 变成 1，169 个测试仍全过。

> **这个 bug 说明**：不真跑一遍，“预算耗尽”这条路径的行为就是猜的。
> 写测试的价值不在“证明对”，在“逼出错”。

**第 4 项验收结果（11/8，4 工具 → 6 工具）：**

新增 `list_documents`（列已收录文档）和 `current_time`（补时间幻觉）。

| 运行 | 动作准确 | 关键点覆盖 | 幻觉 | 应拒答 | 平均 token | P95 |
|---|---|---|---|---|---|---|
| 4 工具（11/7） | 98.0% | 92.2% | 2 | 80% | 6716 | 9363ms |
| 6 工具（14:19） | 98.0% | 83.3% | 3 | 80% | 6885 | 8772ms |
| 6 工具（14:24） | 98.0% | 86.5% | 4 | 100% | 7674 | 10349ms |

**结论 1：动作准确率完全没掉**（三次都是 98.0%）。
新工具被真实调用了（`list_documents` 12 次、`current_time` 6 次），
不是“加了没用”，而是“加了没添乱”。

**结论 2（更重要）：其他指标的差异淹没在方差里。**

同为 6 工具的两次运行：
- 关键点覆盖 83.3% vs 86.5%（差 3.2 点）
- 应拒答 80% vs 100%（差 20 点 —— 只有 5 条题，1 条不同就是 20 点）
- 平均 token 6885 vs 7674（差 789）
- 幻觉 3 vs 4（差 1 条）

**所以「4 工具 92.2% → 6 工具 83.3%，掉了 8.8 点」这个结论不成立** ——
6 工具自己的两次就差了 3.2 点。

**方法论结论（对所有后续 A/B 对比都适用）**：

> 50 条样本的评估集，单项指标波动可达 ±5~20 点。
> **以后做任何 A/B 对比（含第 4 周的四项优化），必须跑 3 次取平均，
> 否则得出的“提升/下降”很可能是噪声。**

唯一稳定可比的是动作准确率（98.0% × 3），因为它由离散的分类决策构成，
不像关键点覆盖那样受答案措辞影响。

#### 业界参考：Anthropic 的 Agent Memory 四层（2026-11-06）

来源：`The components of agent memory`，Anthropic Engineering，2026-11-06（Lance Martin）
<https://www.anthropic.com/research/components-of-agent-memory>

它把“记忆”的边界划得很窄：**只算跨会话保留的知识**；改权重、单次会话内的
上下文学习、把旧轮次压成摘要（compaction）**都不算**。

| 层 | 存什么 | 特点 |
|---|---|---|
| Transcripts 原始记录 | 完整对话、工具调用、执行结果 | **唯一的事实源**，其余层都是它的缓存 |
| Memory Notes 笔记 | Claude 自己写的经验、错误原因、规则 | 会话中随手写，**写的时候就可能写错** |
| Memory Representations 表征 | Wiki、索引、交叉链接 | 从日志和笔记算出来的结构化知识 |
| Injected Context 注入上下文 | 少量高价值索引 | 每次会话开头加载，**必须很短**（Claude Code：`MEMORY.md` 前 200 行 / 25KB） |

**Dreaming（做梦）**：会话之间的离线流程 —— 回头翻 transcripts，按“上层对下层对账”
的原则改错笔记、合并重复、搭 wiki、把最要紧的提到注入层。
一句话原则：**原始日志是事实，其余都是缓存，缓存要定期对账。**

反直觉的实测结论：写 **413 份**笔记的模型在宝可梦任务上只拿 1 枚徽章，
写 **9 份**的拿 4 枚 —— 记忆的关键不是存多少，是筛得准不准、能不能纠错。

**这条数据的可信度**：Anthropic 自测，宝可梦每模型只跑一次，wiki 实验仅 24–25 题，
无第三方复现。另外网传“87% vs 73% 是 dreaming 带来的提升”是错的，那组数字
是部分并购题上“wiki 检索 vs 纯搜索”的对比。

#### 本项目现状：四层一层都没有

| Anthropic 的层 | 本项目 | 说明 |
|---|---|---|
| Transcripts | ⚠️ 部分 | `data/traces/*.jsonl` 有完整记录，但设计用途是调试回放，不是记忆的取证源 |
| Memory Notes | ❌ | 无 |
| Representations | ❌ | 无，且原文自测显示单文档场景无明显收益 |
| Injected Context | ❌ | 无，新会话不带任何历史 |

**所以：任何文档/简历里都不能写“参考 Anthropic 记忆架构实现了 X”。**
本节的用途是记录业界参照系与差距，不代表实现。

#### 如果要做的顺序（按收益排序）

1. 先让 transcripts 可检索（把已有 trace 变成搜索入口），成本最低
2. 再加 `memory_notes`：会话结束时一次 LLM 调用抽 0–3 条，带 `source_trace_id` 可回溯

**优先级低于“把已有的东西证过”** —— 先证明现有能力真的能用。

## 第 4 轮：SSE 流式（已完成 11/8）

### 一个架构决定：`run()` 必须是 `run_stream()` 的收集器

最初打算“不动 `run`，新加 `run_stream`”。问题是：
API 上线跑 `run_stream`，如果测试只覆盖 `run`，
那 174 个测试守的就是一段**永远不会执行的代码**。

改成：`run_stream` 是唯一实现，`run()` 消费它取 `done` 事件。

**逻辑一行不重复，测试覆盖的就是上线路径。**

### 实测事件流（单问题）

```
tool_call  × 2
citation   × 2
token      × 194     ← 真流式，不是跑完再切片
done       × 1
```

### 中途断开：修了一个真 bug

原本收口（`tracer.finish` / 写记忆）在循环**之后**。客户端断开时会跳过，
导致 trace 残缺、对话不进历史。

修复过程中发现两件只有真测才能发现的事：

| # | 发现 | 后果 |
|---|---|---|
| 1 | **实际断连抛的是 `asyncio.CancelledError`，不是 `GeneratorExit`** | 只捕 `GeneratorExit` 会漏——trace 里的 `stop_reason` 会是初始值 `max_steps`（误归因） |
| 2 | **task 被 cancel 后，`finally` 里的 `await` 会立即再抛 `CancelledError`** | `_remember` 里的 `await to_thread` 根本跑不完，记忆依旧丢 |

**修法**：

- `except (GeneratorExit, asyncio.CancelledError)`，**两者都重新抛**
- `await asyncio.shield(self._remember(...))` —— 让内部协程在后台继续
- 新增 `StopReason.CANCELLED`，不把断连归到 `max_steps`
- `partial_text` 在循环外累积，保留已生成的部分

**实测结果：**

```
断开前 trace 行数   948
断开后 trace 行数   949
stop_reason         cancelled        ✅
会话记忆            2 条              ✅
  user:      试用期员工能休年假吗？
  assistant: 我先                        ← 模型刚生成的 2 个字
```

**最后那个“我先”很关键**：说明“保留已生成部分”是真的做了，
而不是只写一句降级文案。

> **这一条在面试里很值钱**：多数人只知道“客户端断开要 finally 收口”，
> 不知道断连抛的是 `CancelledError` 而不是 `GeneratorExit`，
> 更不知道 cancel 之后 `finally` 里的 `await` 会立即失败。

### citation 未验的原因：环境，不是代码

Qdrant 在这台机器上**反复崩溃**：

```
Docker Desktop 启动 → 吃 3.8 GB（可用内存 5379 → 1576 MB）
→ Qdrant 容器起来 → 几十秒后 daemon 退出（WSL 发行版 Stopped）
```

服务端因此一直报 `degraded`，检索全部失败，**没有引用可渲染**。

**但降级路径反而被验证了**：Qdrant 不可用时，Agent 会
（1）尝试 3 次检索、（2）如实说“检索服务故障，不是手册没有”、
（3）自动建 P1 故障工单。**这比正常路径更能说明系统是抗造的。**

### 会话可恢复：刷新不丢对话（已完成 11/11）

**问题**：`session_id` 只活在 JS 内存里，刷新页面就变 `null`，下次提问直接开新会话。
服务端的 SQLite 历史还在，但前端拿不回来。

#### 接口：`GET /qa/session/{session_id}`

```json
{"session_id": "s-0e9d52c20531", "messages": [
  {"role": "user", "content": "年假有几天？"},
  {"role": "assistant", "content": "年假天数按累计工作年限确定…"}
]}
```

两个设计决定：

| 决定 | 理由 |
|---|---|
| **历史不塞进 SSE 的 `done` 事件** | `done` 只该携带“这一轮”。历史每轮都在变长，混进去会让每一帧都变大，前端还得去重 |
| **不存在返 404，不返空列表** | 404 是“这个 id 废了，清掉你本地存的”的明确信号；返空列表会让前端一直复用死 id，看上去像“模型突然忘事” |

出参只暴露 `role` / `content`，存储里多出的键会被裁掉（和 `CitationOut` 同一套思路）。

#### 前端：本地只存 id，后端是唯一真相

```javascript
const SESSION_KEY = "kb_session_id";
sessionId: localStorage.getItem(SESSION_KEY) || null,
```

`restoreSession()` 把四种情况分开处理：

| 状态 | 处理 |
|---|---|
| 无 id | 什么都不做 |
| **401** | 口令问题，**不销毁会话**（否则填错口令就把历史丢了） |
| **404** | 会话真没了，清本地 id 静默开新会话 |
| 200 但无消息 | 会话存在但还没问答，保留占位 |

额外加了「新建会话」按钮：否则刷新后永远接上一轮，用户无法主动开新对话。

#### 实测（公网 47.93.237.92，Playwright + Edge）

| 步骤 | 结果 |
|---|---|
| 第一轮「年假有几天？」 | ✅ 答出 5/10/15 天，`session_id=s-0e9d52c20531` |
| 第二轮「那病假呢？」 | ✅ 答出病假材料 + 80% 工资（承接上文） |
| **刷新页面** | ✅ **user=2 agent=2，与刷新前的 4 条完全一致** |
| **第三轮「我刚才问了你什么？」** | ✅ 「你刚才问了两件事：1. 年假有几天… 2. 病假呢…」——**模型确实读到了历史** |
| 新建会话按钮 | ✅ `session_id=None`，消息清空 |
| JS 报错 | ✅ 无 |

测试：`tests/test_api.py` 新增 3 条（正常序列 / 404 / 剔多余字段），全量 **190 个通过**。

### 三个实现细节

1. **答案区流式用 `insertAdjacentText`**，不重建 DOM
   （每个 token 都 `innerHTML = ...` 会重排整棵树）
2. **`done` 后做一次极简 Markdown 渲染**（加粗/列表/换行）
   流式期间纯文本，因为半截的 `**` 渲染出来是脏的
3. **SSE 解析要留不完整的尾巴**

```javascript
const parts = buf.split("\n\n");
buf = parts.pop();          // 最后一段可能不完整
```

**不这么做**：事件被网络切成两块时 `JSON.parse` 抛异常，表现为“偶尔丢字”。

| 健康检查缓存“启动时失败” | Docker 晚起 3 秒，`/health` 就**永远** degraded | 每次真实探，加 3 秒超时 |

单元测试用 `gen.aclose()` 验过中断标记，但那是 `GeneratorExit`。
真实浏览器断连走 `CancelledError`。两者共用同一个 except 分支，

**四项全过：**

|---|---|

### 两个只有扩语料才会暴露的问题

#### 1. 拒答判定被领域词汇撞了（已修）

第一轮跑完，报告里冒出 **27 条“误拒答”**，但汇总里误拒率是 0.0%。两个数字矛盾。

查下来是两个原因：

| 原因 | 命中数 | 实际情况 |
|---|---|---|
| `未规定` | 16 | 答案里写“该条款**未规定**申请材料”——这是**补充说明**，不是拒答 |
| `知识库中` | 10 | “根据**知识库中**的《员工手册》”——这是**正常引用** |

根因：旧判定是“词出现就算拒答”，而语料变多后答案变长、补充说明变多。
实测 6 条误判里，**4 条的 marker 出现在第 280 字之后**。

**修法两处**：

1. `detect_refusal` 只看答案前 120 字（结论区）
2. 词表改成正则：`(知识库|手册|文档|制度|资料).{0,20}(没有|未|查不到|暂无|无法).{0,20}(规定|条款|信息|内容|条文|相关)`
   —— 拒答措辞太活（“知识库**里**没有…规定”、“知识库中**暂无**…信息”），词表写不尽；
   但“根据知识库中的…”是引用，所以**否定词不能省**。

结果：误判 27 → 16 条，**应拒答率从 0.8 恢复到 1.0**（旧版其实漏判了 R01）。

剩下的 11 条是**词表法的能力上限**，不是 bug：

- “**如果**手册没有单独规定，那么…”—— 条件句，语义上是回答不是拒答
- “有。陪产假 15 天。补充：该条款未说明申请材料”—— 局部声明缺失

报告标签也改成了和汇总同口径（`refused and not citation_ok`），否则会冒出一堆假阳性。

| 题 | 原断言 | 为什么失效 | 改法 |

**D13 是真冲突**（不是语料写错）：

| 题目结构 | 含“制度没写”的推理题 | 基本是“两份文档各取一条规则拼起来” |

这是典型的**自证偏差**：出题人知道答案在哪，会不自觉地让断言贴着原文措辞。

#### 结论三：一个反直觉的发现——老拒答题更不愿意转单

| | 条数 | 动作准确 |
|---|---|---|
| v1/refusal | 5 | **60.0%**（R01 / R05 两条没转单） |
| v2/refusal | 10 | **80.0%** |

v1 的拒答题平均 token **15041**，是全部组里最高的 —— 模型在“答不出来”时会反复检索、展开长解释，
最后选择“如实说没有”而不是“转工单”。

**两种都是合理产品行为。** 真正值得记的是：**同一道题（R01/R05）在不同运行里会时而转单时而直接答**，
这个决策不稳定。

#### 所以：以后报指标必须带 batch

单看 89.4% 会让人以为系统变强了；实际上 **v2 的多跳题把平均值抬高了 4.5 个点**。
跑 A/B 对比时，要用 **同一批次** 做对比，不能拿“100 条的新版”比“50 条的旧版”。

### v2 多跳题加难尝试（11/12 晚，结果不如预期）

把 24 条 v2 多跳里的 15 条最直白的改成**场景题**（给具体日期/金额/人数，让模型自己判断适用哪条规则）。

#### 改动思路

| 原题 | 改后 | 新增的推理点 |
|---|---|---|
| 病假要交什么材料 | 只交了社区医院的诊断书，HR 说不合规，合理吗 | 社区医院 ≠ 二级以上 |
| 出差餐费住宿怎么报 | 去广州出差 3 天能报多少 | 广州→一线；3×100=300 |
| 请 3 天年假找谁批 | 工龄 5 年想休 4 天，找谁批 | 4 天落在 3–5 区间 |
| 招待费人均标准 | 2 重要客户 + 1 一般客户，预算按多少 | **“就高标准执行”那句** |
| 忘记打卡能补几次 | 本月已补 3 次，还能补吗 | 额度已用满 |
| 加班要提前申请吗 | 故障加班到 11 点没申请，算加班吗 | 紧急故障属于例外 |

**断言设计**（用户明确要求避开“必须出现某个词”）：
- `key_points` 只放**中间结论**（“就高标准”“超额”“分管副总”），不放原文数字
- `must_not` **全部清空**（15 条里 13 条是空），改由 key_points 正向验证

#### 结果：token 涨了，准确率反而涨了

| 指标 | 加难前 | 加难后 | 变化 |
|---|---|---|---|
| kp 总数 | 79 | 75 | -4 |
| kp 命中数 | 73 | 71 | -2 |
| 每条平均 kp 数 | 3.29 | 3.12 | -0.17 |
| **平均 token** | **5722** | **6269** | **+547（+9.6%）** |
| **平均延迟** | **4059ms** | **4808ms** | **+749（+18.4%）** |
| **加权覆盖率** | **92.4%** | **94.7%** | **+2.3%** |
| Recall@5 | 100% | **95.8%** | ↓ 4.2（M29 未命中） |
| 动作准确 | 100% | 100% | — |

#### 诚实的结论：场景化只增加了“思考量”，没增加“错误率”

逐条看，**24 条里只有 2 条覆盖率下降**：

| 题 | 变化 | 为什么 |
|---|---|---|
| **M31** | 4/4 → **2/3** | 唯一真正生效的：模型**没答出“就高标准执行”和 1200** |
| M27 | 4/4 → 3/4 | 漏了一个考点 |
| 其余 22 条 | 持平或上升 | — |

**为什么没变难：**

1. **kp 数从 3.29 降到 3.12** —— 分母变小，覆盖率自然升。这是我自己挖的坑。
2. **断言仍然偏宽**：把 key_points 写成“分管副总”这种**名词**，模型只要提到就命中；
   真正的推理题应该要求**结论**（如“已超期”“不能补”“按 1200”）。
3. **场景描述主要增加的是 token，不是错误**：模型多看几行上下文就能答对。
   证据：M22 的 token 从 4749 涨到 9002（+90%），但依然 3/3。

#### 唯一成功的例子：M31

它和其余 14 条的区别是：**答案不在任何一句话里**。
必须把“2 重要客户 + 1 一般客户”和文档里“同一次招待涉及多类对象的按就高标准执行”
两条信息**接起来**，才能得出 1200。其他题只是“把场景关键词映射到对应条款”，一步就能到。

**结论：要真正加难，应该复制 M31 的模式（要求跨句组合推理），
而不是只给问题加一个场景壳。**

#### 一个额外的真实发现

**M29 检索未命中**（Recall 100% → 95.8%）。它是场景化的：

```
原：“旷工怎么处理？”          → 命中 2.2 节
现：“我上周连续 3 天没去上班也没请假，HR 说可以开除我” → 没命中
```

**用户真实就是这么问的。** 所以场景化确实降低了检索命中率——
这不是退步，是把“口语化查询对检索的影响”这个真实难点暴露出来了。

### 一个必须记下来的方差证据

同一配置（6 工具、54 chunk、同一批题）连着跑三次：

```
动作准确  98.0%  →  98.0%  →  96.0%
```

**同一套题、同一个模型、同一份语料，动作准确率能差 2 个点**（R05 在最后一次从
ticket 翻成了 answered）。

这条直接支持了之前那个结论：**50 条样本的单项指标方差 ±5~20 点，A/B 对比必须多次取平均**。

### 跑通之前踩的三个坑

三条都不是「配置写错」，而是**只有真的在容器里跑才会暴露**的问题：

#### 坑 1：apt 连不上 deb.debian.org，构建卡满 5 分钟后 exit 100

同一台机器、同一时刻在容器里实测三个源：

| 源 | 结果 |
|---|---|
| `deb.debian.org` | 200，但单请求 **16.6 秒**，Packages 索引直接超时 |
| `mirrors.tuna.tsinghua.edu.cn` | **403 Forbidden**（0.4 秒返回） |
| `mirrors.aliyun.com` | **200，0.11 秒** |

修法：构建前换阿里云源。注意 Debian 12+ 把源写在
`/etc/apt/sources.list.d/debian.sources`，老版本是 `/etc/apt/sources.list`，两处都要兜：

```dockerfile
RUN for f in /etc/apt/sources.list /etc/apt/sources.list.d/debian.sources; do \
        [ -f "$f" ] && sed -i 's|http://deb.debian.org|http://mirrors.aliyun.com|g' "$f"; \
    done; \
    apt-get update && apt-get install ...
```

#### 坑 2：hf-mirror 不支持 Xet，下载会「静默卡住」

新版 `huggingface_hub` 默认走 Xet 传输协议，`hf-mirror.com` 不支持。
失败方式极其坑人：**不报错、不超时、进度条停在 `3/5` 十分钟不动**。

修法：`HF_HUB_DISABLE_XET=1` 退回普通 HTTP。慢（实测 ~90KB/s，95MB 要 17 分钟），
但能跑完，而且只跑一次——烤进镜像层后重建不再下载。

#### 坑 3：模型烤进镜像了，运行期却当成空缓存重下 95MB（最隐蔽）

两个原因叠加，缺一不可：

**① `Embedder.from_settings` 硬编码了 Windows 缓存路径**

```python
# 改之前
cache_dir=Path(r"E:\DevCaches\fastembed"),
```

在 Linux 里这**不是一个路径**，而是一个带反斜杠的普通目录名，
相对 `/app` 解析成 `/app/E:\DevCaches\fastembed` —— 永远不存在。
fastembed 于是每次都判定「没有缓存」，重新下载 95MB，
`/health` 卡在启动期二十多分钟。

```python
# 改之后：容器读环境变量，本地开发仍走 E 盘
cache_dir=Path(os.getenv("FASTEMBED_CACHE_PATH") or r"E:\DevCaches\fastembed"),
```

**② fastembed 默认缓存目录的属主不对**

fastembed 默认缓存到 `tempfile.gettempdir()/fastembed_cache`。构建期是 root，
运行期是 appuser —— 缓存目录不可写，实测 `touch` 直接 Permission denied，
拿不到锁文件同样判定缓存无效。

修法（Dockerfile，接在模型预热之后）：

```dockerfile
RUN mv /tmp/fastembed_cache /models/fastembed_cache
ENV FASTEMBED_CACHE_PATH=/models/fastembed_cache
```

`mv` 是同层内重命名，不产生第二份；`/models` 本来就在
`chown -R appuser:appuser /app /models` 里，属主一并解决。

**为什么 `ENV` 放在预热之后**：Docker 的层缓存从第一处改动往后全部失效。
放进顶部那个 `ENV` 块，预热层立刻作废，又得重下 95MB。放在预热之后，
预热层能命中缓存（实测重建只花几十秒）。

### 访问控制：口令 + 限流（已完成 11/11）

公网暴露前必须先有这一层：`/qa/ask` 背后是 DeepSeek 的按量计费接口，
没有口令等于把 key 交给扫描器。

**实现**：`app/api/auth.py`，纯 ASGI 中间件。

| 设计点 | 为什么 |
|---|---|
| **纯 ASGI，不用 `BaseHTTPMiddleware`** | 后者会包住 `send`，把响应体缓冲在自己的层里 —— SSE 会从“逐 token”退化成“攒完再发” |
| **白名单 `/`、`/health`、`/static/*`** | 首页不放行就没地方输口令；`/health` 要给探活和状态灯用 |
| **`/docs`、`/openapi.json` 不白名单** | 公网暴露接口清单等于给扫描器送地图 |
| **先限流、后鉴权** | 反过来的话，猜口令不消耗配额，等于免费重试 |
| **`hmac.compare_digest`** | `==` 在第一个不同字节就返回，能被时序攻击逐字节猜出口令 |
| **滑动窗口（deque 存时间戳）** | 固定窗口有边界问题：第 59 秒打满、第 61 秒又能打满 |

**配置**（`.env`，见 `.env.example`）：

```bash
ACCESS_TOKEN=              # 空 = 不鉴权（本地开发/测试）
RATE_LIMIT_PER_MINUTE=60
```

**实测（11/11，`ACCESS_TOKEN=test-secret-123`）**：

| 请求 | 结果 |
|---|---|
| `GET /health` 无 header | 200 ✓ 白名单 |
| `GET /` 无 header | 200 ✓ 白名单 |
| `GET /documents` 无 header | **401** ✓ |
| `GET /documents` 错口令 | **401** ✓ |
| `GET /documents` 对的口令 | 200 ✓ |
| `GET /docs` 无 header | **401** ✓ |
| `POST /qa/ask/stream` 无 header | **401** ✓ |
| `POST /qa/ask/stream` 带 header | 200，**token × 176 / tool_call × 1 / citation × 1 / done × 1** ✓ 流式未被缓冲 |
| 连打 `/health` | 第 **53** 次首次 429（此前已消耗 8 次，额度 60，完全吻合） ✓ |
| 前端（Playwright） | 无 JS 报错；口令存 localStorage；文档列表加载出「员工手册.pdf · 6 页 · 14 chunks」 ✓ |

**测试**：`tests/test_auth.py` 10 条，全量 **187 个通过**。

**已知边界**：限流状态在进程内存，多 worker 时额度 = 配置 × worker 数，重启清零。
要跨进程得放 Redis —— 对演示站是过度设计。

#### 新踩的坑：Linux 上的 `data/` 目录权限

容器里以 `appuser`（uid 10001）运行，而解压出来的 `data/` 归 root：

```
sqlite3.OperationalError: unable to open database file
ERROR:    Application startup failed. Exiting.
```

表现是容器 **反复重启**（`restart: unless-stopped`），`docker ps` 显示 `Restarting`。

**修法**：`chown -R 10001:10001 /root/kb-agent/data` 后重建容器。

**为什么本机永远碰不到**：Docker Desktop 的 bind mount 会把权限放开，
容器里怎么写都行；Linux 上 bind mount 保留宿主机的 uid/gid，权限是真生效的。
**这类问题只有真机部署才会暴露。**

#### 口令策略：公开 + 限流（11/11 调整）

第一版口令是 24 位随机串，README 里写的是「见简历 / 私信」。
**问题是面试官点开链接会打不开**，大概率直接关掉。

改成公开口令 `kb-demo-2027`，同时把限流从 60 降到 **20 次/分钟/IP**：

| 理由 | 说明 |
|---|---|
| 演示价值 > 保密 | 一个面试官最多点几次，能打开比猜口令重要 |
| 扫描器不会打它 | `/qa/ask` 需要知道接口路径和 JSON 结构，不是通用扫描目标 |
| 成本有上限 | 20 次/分钟 × 60 分钟 × 约 5000 tokens，封顶后自然停 |

**这是一个明确的取舍，不是疏忽。** 真要做成产品，得换用户体系 + Redis 限流
+ 按用户配额，而不是一个共享口令。

服务器 `curl https://github.com` 返回 `000`，`git clone` 直接不可行。

### 为什么并存，不直接替换 SQLite

| 方案 | 问题 |
|---|---|
| 直接换 | ①190 个测试全部要连 MySQL，CI 变慢且脆弱 ②本地开发要先起容器 ③**运维“为什么换”这个问题还是答不出来** |
| 并存 + 可切换 | ①测试仍跑 SQLite，秒级 ②本地零依赖 ③**切换依据本身就是最好的面试答案** |

**一句话**：直接换是把问题藏起来，并存是把判断讲出来。

### 四类关键决定

| 决定 | 理由 | 不这样做会怎样 |
|---|---|---|
| **不抽 Repository 接口，只两套类** | 方法签名一致就够；抽接口要两套实现各写一次空方法 | 多一层抽象但零收益 |

### 并发建单：从 3/20 到 20/20（11/13 补验）

上一版 `_next_id` 用的是「查 tickets 的最大 id + 1」。当时我在讲解里承认了
“并发会撞主键”，但没实测。补验结果比预想的严重：

| 版本 | 20 线程并发结果 |
|---|---|
| 旧（查 max id + 1） | **成功 3 / 20**，17 个 `IntegrityError` |
| 新（序列表 + 行锁） | **20 / 20**，零冲突 |

实际报错：

```
Duplicate entry 'T-20261113-0003' for key 'tickets.PRIMARY'
```

#### 为什么旧实现必撞

**MySQL 的普通 `SELECT` 是快照读（consistent read），不加任何锁。**

```
时刻 T1   20 个事务同时读到最大序号 = 0003
时刻 T2   20 个事务都算出 0004
时刻 T3   第一个插 0004 成功，剩下 19 个全部主键冲突
```

事务在这里**保护不了**任何东西——事务隔离保证的是“看到一致的快照”，
而两个事务看到同一个快照，结果就是算出同一个号。

**SQLite 没这个问题**：它的写是串行的（写事务持库级写锁），
所以 SQLite 版保持原实现，不需要序列表。这也是两个后端实现不完全对称的原因。

#### 新实现：序列表 + 行锁

```sql
CREATE TABLE sequences (name VARCHAR(64) PRIMARY KEY, value BIGINT NOT NULL);

INSERT INTO sequences (name, value) VALUES (%s, LAST_INSERT_ID(1))
ON DUPLICATE KEY UPDATE value = LAST_INSERT_ID(value + 1);
SELECT LAST_INSERT_ID();
```

三个关键点：

| 点 | 作用 |
|---|---|
| **`ON DUPLICATE KEY UPDATE`** | 对该行加排他锁，20 个事务在这里**排队** |
| **`LAST_INSERT_ID(expr)`** | MySQL 技巧：把 `expr` 写进连接级计数器并返回它，省一次 `SELECT value` |
| **`LAST_INSERT_ID()` 是连接级** | 必须在同一连接读；事务内同一个 cursor 就是同一条连接 |

#### 一个容易漏的坑：首次取号要和历史对齐

计数器从 0 开始时，第一次取号拿到 `0001`——而库里已经有 `0001`-`0003`（旧版本建的），
**直接撞历史单号**。

所以首次取号前先对齐：

```sql
SELECT COALESCE(MAX(CAST(RIGHT(id, 4) AS UNSIGNED)), 0)
FROM tickets WHERE id LIKE 'T-20261113-%';
```

只在序列表里**没有当天行**时做（一次查询），不是每次建单都扫表。

#### 验证方法

`scripts/verify_mysql_concurrency.py`：

- 用 `threading.Barrier` 让 N 个线程**同时出发**，最大化竞态窗口
- **连接池必须 >= 线程数**（`MYSQL_POOL_SIZE=20`），
  否则请求在池里排队，测到的是“池的串行化”而不是“数据库的竞态”
- 统计：成功数、异常分类、单号去重、库内新增条数

### 前端 SSE 解析要点（已完成，留作参考）

四个区块（约束 C9/C10）：

| 区块 | 对接 | 要点 |
|---|---|---|
| 上传面板 | `POST /documents/upload` | 显示 `chunk_count`；幂等重传应返回相同结果 |
| 问答区 | `POST /qa/ask/stream` | **`fetch + ReadableStream` 手工解析 SSE**（不能用 `EventSource`，因为我们用 POST） |
| trace 面板 | 从 SSE 的 `tool_call` 事件累积 | 可折叠列表，显示工具名 + 参数 |
| 评估页 | `GET /documents` + 静态报告 | 指标打表 |

**前端解析 SSE 的关键**（网络分片不保证按事件边界到达）：

```javascript
let buf = "";
while (true) {
  const {done, value} = await reader.read();
  if (done) break;
  buf += decoder.decode(value, {stream: true});
  const parts = buf.split("\n\n");
  buf = parts.pop();           // ← 最后一段可能不完整，留着
  for (const part of parts) { /* 解析 event: / data: */ }
}
```

**不这么做会怎样**：一个事件被网络切成两块，`JSON.parse` 直接抛异常，表现为“偶尔丢字”。
