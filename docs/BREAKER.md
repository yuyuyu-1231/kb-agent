# 三重熔断验证报告

> 用剧本化的假模型精确构造三种异常行为，验证 Guard 能不能拦住。
> 熔断依赖「模型行为异常」，用真模型无法保证复现，所以用假模型。

## 一、三条熔断路径

| 场景 | stop_reason | 步数 | 是否触发降级文案 | 实际返回的开头 |
|---|---|---|---|---|
| A 重复动作 | `loop_detected` | 1 | 是 | 检测到重复的检索动作，为避免无效消耗已停止。建议补充更具体的信息，或 |
| B 轮数超限 | `max_steps` | 3 | 是 | 这个问题需要查证的信息较多，已达到本次处理的最大轮数。建议提交工单由 |
| C 预算耗尽 | `budget_exhausted` | 1 | 是 | 本次查询涉及的内容超出处理预算，已停止。建议把问题拆小后再问。 |

### 判定

- ✅ A 熔断原因是重复动作
- ✅ B 熔断原因是轮数超限
- ✅ C 熔断原因是预算耗尽
- ✅ B 恰好跑满 3 轮（max_steps=3）
- ✅ 三条都返回了降级文案（answer 非空）
- ✅ stop_reason.value 是下划线格式而不是枚举名

## 二、`_pad_skipped_tool_calls`（从未执行过的代码）

构造：一批 2 个 tool_calls，第 1 个执行、第 2 个被熔断拦下。

| 检查项 | 结果 |
|---|---|
| 补了几条占位消息 | 1（期望 1） |
| 占位的 tool_call_id | ['c2']（期望 ['c2']） |
| role | `tool`（期望 tool） |
| 内容 | `{"error": "已熔断，本次工具调用未执行"}` |

**✅ 占位补全正确**

> 为什么这条重要：如果熔断发生在批次中间而不补占位，
> messages 里就会有一个没有对应 tool 消息的 tool_call_id。
> 协议要求每个 id 都必须有回应，否则下次请求直接 **400**。

## 三、降级文案（用户会直接看到的话）

| stop_reason | 文案 |
|---|---|
| `max_steps` | 这个问题需要查证的信息较多，已达到本次处理的最大轮数。建议提交工单由人工跟进。 |
| `budget_exhausted` | 本次查询涉及的内容超出处理预算，已停止。建议把问题拆小后再问。 |
| `loop_detected` | 检测到重复的检索动作，为避免无效消耗已停止。建议补充更具体的信息，或提交工单。 |
| `llm_error` | 模型服务暂时不可用，请稍后重试。 |

## 四、结论

三条熔断路径全部跑通，占位补全正确，降级文案正常返回。

**验证边界（说清楚）**：

- 用假模型构造，验的是「Guard 能否拦住」，不是「真模型会不会异常」
- `repeat_threshold=2` 意味着同一个 (name, args) 出现第 2 次就熔断
  —— 这是刻意设小的值，生产环境可以调大以避免误杀
- 真模型下这些场景概率低（50 条评估里 `loop_detected` 0 次），
  但这不代表不该有熔断 —— 它是兜底，不是常态
